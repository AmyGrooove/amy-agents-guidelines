# Архитектура Amy: требования и проект решений

Статус: структурная миграция выполнена в версии 2.19.2 по согласованной схеме. Исходная версия до миграции: 2.19.1. Функциональные доработки модулей и навыков остаются отдельным следующим этапом.

## Цель и порядок работы

Сделать структуру понятной владельцу проекта и привести код к его стандартам frontend/backend с учётом того, что Amy — библиотека и CLI на Node.js, без React и NestJS.

Terra выполняет структурную миграцию по этому документу, сохраняя существующее поведение. Сквозной запуск, новые алгоритмы выбора агентов и прочие функциональные изменения в этот этап не входят. Пункты следующего обсуждения не блокируют перенос существующего кода.

## Требования пользователя

- Переименовать корневой `assets/` в `public/`, обновить ссылки на иконку в манифесте и других потребителях.
- Разложить `references/` по тематическим папкам. Сохранить доступ к справочникам из навыков; обновить относительные ссылки.
- Привести `scripts/` к понятному стилю: осмысленные имена переменных и функций, пустые строки между логическими блоками, читаемый код. Имена файлов — lower camel case. Собственные сообщения скриптов — на русском.
- Перевести имена навыков в camelCase только при совместимости с требованиями Codex; иначе сохранить требуемый формат.
- Перенести исходники `runtime/src/` в корневой `src/`.
- В `src/` использовать четыре слоя: `shared`, `entities`, `modules`, `app`. Последнее решение пользователя заменяет предыдущую схему из трёх слоёв.
- `app` — верхний слой сборки и сквозного выполнения. `TaskWorkflow` и `CodexExecution` размещаются здесь, а не в `modules`.
- Использовать правила кода и структуры объектов из собственных навыков плагина. Эта задача включает приведение переносимого production-кода к этим правилам, а не только смену путей.
- `shared` содержит общие переиспользуемые функции, константы, типы и другие общие объекты.
- `entities` содержит отдельные сущности с принадлежащими им функциями, константами и типами по модели frontend/backend.
- Папки модулей и их основные функции именовать в PascalCase. Основная реализация — `modules/<ModuleName>/core/<ModuleName>.ts`, например `modules/TaskAnalysis/core/TaskAnalysis.ts`; не использовать `<name>.service.ts`. Модуль — функциональный объект, без обязательного класса, React или NestJS. Собственные `types`, `static`, `functions` и минимальный `index.ts` добавлять по необходимости.
- Для функций проверки типа в `shared` использовать `is<Type>` без префикса `check`, например `isRecord`. При реализации обновить соответствующее правило навыков через общий справочник `references/standards/typescript-and-objects.md` и проверить связанные инструкции. Это узкое исключение для проверки типа в shared, не переименование всех предикатов и валидаторов.

## Проверенные ограничения

- Имена навыков и их папок сохранить в kebab-case. Agent Skills требует lowercase letters, digits, hyphens и совпадение имени с папкой; `SKILL.md` сохраняет обязательное имя. Источник: https://agentskills.io/specification, раздел name field. Локальный валидатор skill-creator также отклоняет camelCase.
- В манифесте текущие пути иконок указывают на `./assets/icon.svg`; после переноса они должны указывать на `./public/icon.svg` и пройти проверку манифеста.
- Существующий код использует TypeScript, NodeNext и сборку в `runtime/dist`; пути связаны с package scripts, CLI, вычислением корня плагина, тестовыми потребителями и документацией. Переименование требует миграции этих связей.
- Формат backend endpoints сейчас описан для NestJS. Переносить в Amy NestJS, декораторы, HTTP-контроллеры и DTO только ради похожих папок не требуется.
- Один факт повторного использования не делает объект частью `shared`: контракты задачи и результата специфичны для Amy.
- Последнее решение пользователя: в структурном этапе удалить текущие тесты Amy и обслуживающую их конфигурацию. Не создавать и не восстанавливать тесты до завершения полной доработки плагина. Удаление разрешено явно; повторное согласование не требуется. Содержимое тестов для удаления читать не нужно.
- Это решение относится к тестам самого репозитория Amy. Сохранить навык `author-typescript-test`, справочник `testing.md` и функциональный модуль `Evaluation`: они не являются тестовым набором репозитория. Не распространять временный отказ от тестов на проекты пользователей плагина.

## Архитектурные решения

Пользователь принял разделение ответственности и попросил зафиксировать все выделенные папки для создания Terra. Структура ниже является целевой; функциональность новых объектов ещё не проектируется.

### Границы слоёв

- `shared`: переносимые примитивы без знаний о задаче Amy, стратегии или роли агента.
- `entities`: понятия Amy и принадлежащие им данные, проверки, функции и константы; список папок приведён ниже.
- `modules`: прикладные сценарии, например классификация задачи, выбор стратегии, оценка завершения; используют сущности и общие объекты.
- Направление импортов: `app` может импортировать `modules`, `entities`, `shared`; `modules` — `entities`, `shared`; `entities` — `shared`. Нижние слои не импортируют верхние. Между объектами одного слоя — минимальный публичный API, без циклов. Сквозной сценарий нескольких модулей принадлежит `app/TaskWorkflow`.
- Переиспользование, ввод/вывод и наличие класса сами по себе не определяют слой. Настройки, хранилище, события и сборку Runtime распределить по ответственности после анализа зависимостей.
- Сборка существующего Runtime и CLI принадлежат `app`. Тонкие `src/cli.ts` и `src/index.ts` остаются совместимыми внешними точками входа; внутренние объекты не импортируют из них.

### Форма объектов

Применять `references/standards/typescript-and-objects.md` и `references/standards/project-architecture.md` в пределах согласованной структуры Amy:

- отдельная папка объекта, основной код в `core`, минимальный `index.ts`;
- собственные `types`, `static`, `functions` только при реальной необходимости;
- обычные функции и их папки — lower camel case; модули и их основные функции — PascalCase; интерфейсы — `IName`, типы — `TName`, константы — `SCREAMING_SNAKE_CASE`;
- функции проверки типа в shared — `is<Type>`, например `shared/functions/checks/isRecord/core/isRecord.ts`; при доказательстве типа сохранять корректный TypeScript type predicate;
- обычно один объект на файл; именованные экспорты, стрелочные функции, явные логические блоки;
- не добавлять пустые папки, комментарии и лишние абстракции; исключение — явно запрошенные папки будущих `app/TaskWorkflow/core` и `app/CodexExecution/core`;
- публичные импорты между объектами; относительные внутри объекта; без глубоких импортов, циклов и общих экспортных файлов на весь слой;
- механизм алиасов согласовать с реальным запуском собранного Node.js-кода, не ограничиваться успешной проверкой TypeScript.

### Уточнения для реализации без изменения поведения

- Правила четырёх слоёв и PascalCase-модулей относятся к самой Amy. Не заменять ими стандарты frontend/backend для пользовательских проектов. Единственное согласованное общее изменение навыков сейчас — правило `is<Type>` для проверки типа в shared.
- Функциональная форма основной точки входа модуля не требует переписывать существующие объекты с состоянием в функции. Сохранить публичные классы, конструкторы, методы и жизненный цикл, разместив их как собственные объекты. Основная функция модуля должна иметь реальную существующую ответственность; не добавлять искусственный запуск всех операций ради файла `<ModuleName>.ts`.
- Сохранить имена CLI-команд, JSON-поля, статусы, схемы, capability IDs, настройки и форматы сохранённых данных. Русификация в этом этапе относится к собственным человекочитаемым сообщениям scripts, а не к машинному API.
- Алиасы должны работать и при прямом запуске собранного JavaScript на поддерживаемой версии Node.js. Terra выбирает совместимый механизм без новых runtime dependencies; одних TypeScript paths недостаточно. Проверить разрешение импортов запуском существующих безопасных CLI-команд `status`, `capabilities`, `inventory` и импортом публичного API. Это разовые проверки запуска, не создание тестового набора; не запускать команды, изменяющие данные пользовательского проекта.
- Перед переносом зафиксировать в рабочем контексте доступные внешние экспорты и CLI-команды, после переноса сверить их. Успешная сборка сама по себе не подтверждает сохранение API. Отдельный файл отчёта не требуется.
- Проверять миграцию по частям: контракты и shared, затем группы modules, затем app. Не компенсировать ошибки ослаблением strict-настроек, добавлением any, отключением проверок или молчаливым удалением экспортов.

### Размещение сквозного выполнения

По последнему решению пользователя обе ответственности относятся к верхнему слою `app`:

- `app/TaskWorkflow/core/TaskWorkflow.ts` будет проводить задачу через анализ, контекст, маршрутизацию, выполнение, проверку и завершение. Управляет переходами и ограниченным исправлением, используя решения профильных модулей; не дублирует их правила.
- `app/CodexExecution/core/CodexExecution.ts` будет представлять границу исполнения: передать назначение доступному механизму Codex и получить результат. Он не выбирает самостоятельно стратегию или модель.
- `TaskWorkflow` зависит от публичного API исполнителя и профильных модулей. `CodexExecution` не импортирует `TaskWorkflow`; оба используют контракты из entities.
- Реальный способ передачи управления между TypeScript и инструментами Codex ещё не выбран и не проверен. Наличие функции в Node.js не даёт ей доступ к инструментам текущего чата. До реализации определить доступный механизм интеграции; не подменять реальный запуск фиктивным результатом.
- Эта связка — функциональная доработка следующего этапа. Сейчас создать запрошенные каталоги `app/TaskWorkflow/core` и `app/CodexExecution/core`, но не добавлять фиктивные реализации, пустые экспорты или успешные ответы-заглушки. Пустые папки не сохраняются Git; не добавлять `.gitkeep` или README для их сохранения. Целевая структура закреплена этим документом.

### Скрипты и сборка

- `scripts/check-generated.mjs` → `scripts/checkGenerated.mjs`.
- Удалить `scripts/run-tests.mjs`; не создавать `scripts/runTests.mjs`. Это заменяет прежнее требование переименования тестового runner.
- Удалить `runtime/tests/`, `tsconfig.test.json` и generated-каталог `runtime/.test-dist/`, если он существует. Перед рекурсивным удалением проверить абсолютные пути и принадлежность этому репозиторию; использовать нативные операции PowerShell с LiteralPath.
- В `package.json` удалить `test` и `test:compile`; `typecheck` должен проверять только production-код, без тестовой конфигурации. `check` должен выполнять проверку production-типов, сборку и проверку generated-файлов без тестов. Сохранить ошибки проверок и ненулевой код завершения при сбое.
- Удалить устаревшие ссылки на тестовые команды и конфигурацию из актуальных инструкций, package scripts и `.gitignore`. Исторические сведения о прежнем покрытии не выдавать за действующие проверки; не переписывать несвязанные справочники.
- Сохранить назначение, коды завершения и диагностические данные оставшегося скрипта. Переводить собственные сообщения; не менять машинные идентификаторы и не обещать перевод вывода стороннего компилятора.
- Для структурного этапа сохранить `runtime/dist/` и `runtime/.generated-check/`: меняется расположение исходников, но не публичный путь сборки. Корневой `dist/` отложен. `runtime/` больше не содержит production-исходников и тестов.
- После выбора путей обновить конфигурацию сборки, package scripts, `.gitignore`, поиск корня плагина, документацию, инвентаризацию и разрешённые потребители API.

Существующий внешний `index.ts` сохраняет согласованный публичный API библиотеки, но не используется как внутренний общий barrel.

Контракты entities не должны импортировать типы из modules. Если модуль передаёт свой результат другому модулю или app, выделить общий контракт в сущность, которая владеет его смыслом. Низкоуровневые объекты получают нужные зависимости через параметры, а не импортируют `app/Runtime`. Старые независимые capabilities внутри Telemetry сохраняют независимость и прежние идентификаторы.

## Порядок структурной реализации

1. Проверить рабочее дерево и применимые инструкции. Читать существующий production-код по переносимым объектам; исключать содержимое тестов и stories.
2. Перенести иконку и справочники по карте; обновить ссылки в манифесте, навыках, README и архитектурной документации. Зафиксировать правило `is<Type>` в общем справочнике навыков.
3. Выделить shared и контракты entities, затем перенести modules и существующую сборку в app. Привести код к согласованной форме объектов и именованию.
4. Сохранить внешние экспортируемые имена через явные совместимые экспорты или адаптеры к новым основным функциям; не ломать сигнатуры ради PascalCase. Не переносить контракт в shared только для устранения ошибки импорта.
5. Создать согласованные папки будущих app-объектов без реализации. Не выдавать их наличие за работающий harness.
6. Обновить rootDir/include production-сборки на `src`, сохранив output и публичные точки входа. Перепроверить вычисление pluginRoot после изменения глубины файлов, discovery/inventory и ссылки на исходники.
7. Удалить тесты, тестовый runner и конфигурацию по перечню выше. Переименовать и привести к стандартам `check-generated.mjs`, обновить команды проверки. Новые тесты не создавать.
8. Выполнить production-сборку, проверку манифеста/skills/ссылок и статический контроль импортов и форматирования. Обновлённый `pnpm check` запускать после проверки, что он больше не вызывает тесты. Если обнаружится зависимость от внутреннего старого пути, сохранить совместимость либо явно описать ограничение; не скрывать его.
9. Обновить AGENTS.md с новыми путями исходников и четырьмя слоями. Для совместимого структурного изменения повысить PATCH на 1 в обеих версиях (от 2.19.1 — 2.19.2); перед выпуском проверить фактическую версию. Выполнить принятый процесс синхронизации и переустановки, без коммитов и cachebuster.

## Следующее обсуждение — не входит в структурный этап

1. Проверить способ интеграции с Codex и спроектировать выполнение в `app/TaskWorkflow` и `app/CodexExecution`.
2. Разобрать функциональные изменения каждого модуля и навыка, включая выбор модели, сбор контекста и статистики.
3. Вернуться к проектированию тестов после завершения полной доработки плагина. До этого использовать production-сборку, проверку типов, манифеста и ссылок; не представлять эти проверки как доказательство полного функционального покрытия.

## Критерии будущей реализации

- Все согласованные пути и объекты соответствуют утверждённой карте; нет обратных импортов и циклов.
- Поведение модулей и публичные данные сохраняются, кроме отдельно согласованных функциональных изменений.
- Навыки находятся по прежним именам; все ссылки на справочники и иконки разрешаются.
- Сборка создаётся из исходников, API и CLI работают по согласованным путям; изменения generated-файлов вручную исключены.
- Текущие тесты и обслуживающие их команды удалены; новые тесты не добавлены. Навык для написания тестов и модуль Evaluation сохранены. Проверены манифест, навыки, ссылки и production-код; непроверенное поведение обозначается явно.
- После реализации выполняется установленный процесс выпуска: SemVer без cachebuster, синхронизация из исходного репозитория, переустановка из настроенного marketplace и сверка файлов. Текущая запись обсуждения не является выпуском плагина.

## Следующий этап обсуждения

Разобрать функциональные модули и навыки: назначение, входы, выходы, зависимости и нужные изменения. Целевая функция Amy — явный запуск задачи, подбор ресурсов для исследования и реализации, проверка результата, сопутствующая запись данных, аналитика и предложения улучшений по запросу. Эти функции не реализуются автоматически вместе с переносом папок.
